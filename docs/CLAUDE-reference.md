## Project

A sales lead tracker for Salcomp, built on a Kanban board: each card is a lead and each column a sales stage (1st Contact, F2F Meeting, RFI, Proposal, Award, Lost). Each column's commercial meaning is its `stage_kind` (`open` / `won` / `lost`), never its title: titles are display text an admin can rename without changing any report. Cards carry structured lead fields (company, contact, deal value + currency, expected close date, lead source, product line, assigned salesperson), and a Reports screen aggregates them. Also: drag-and-drop, multi-user auth (admin/member roles), and an AI chat sidebar that can create/edit/move cards and fill in lead fields. Next.js frontend, FastAPI backend serving the static Next.js export at `/`, SQLite database, packaged as a single Docker container. AI calls go through OpenRouter (`openai/gpt-oss-120b`).

Auth: the first user ever created (via a dedicated setup screen) becomes admin; further admins are only ever created or promoted with the server-side `backend/admin_cli.py` (no HTTP path grants admin); an admin can create further users (always role "member") from a "Manage Users" screen, and anyone can self-sign-up by email (also always "member"): the sign-in screen's "Sign up" asks for an email, the backend emails a single-use link (`/?signup_token=<random token>`), and the page it opens sets the password and then returns to the login screen. Self-signed-up users' email is their username. "Forgot my password?" on the login screen takes a username or email, answers identically whether or not the account exists, and emails a single-use 1-hour reset link (`/?reset_token=<random token>`) to accounts that have an email. Boards are shared across all authenticated users — not isolated per owner — but the board's structure (creating/editing/deleting boards and columns) is admin-only. `SECRET_KEY` must be set (no default; the app refuses to start otherwise) — see `docs/SECURITY.md`. Beyond user creation, role also gates card operations: members can create cards (assigned to themselves) and move them only to a column further right (or reorder within a column), never back to an earlier column; a member edits only cards assigned to them; only admins can assign/reassign, delete cards or move them backward (assignment changes and deletions are audited in `audit_events`). A member's edit to a card's title/details is logged to `card_edit_history` and flips the card's `has_member_edits` flag (shown as an "M" badge with a history modal in the UI); admin edits are not logged. These rules apply identically whether the change comes from the REST routes or the AI chat sidebar — both funnel through `backend/card_rules.py` so the two can't drift. Local-only via Docker.

## Commands

### Backend (`backend/`, Python 3.11+, managed with `uv`)
```bash
cd backend
uv sync                          # install deps (or: pip install -e .[dev])
uv run uvicorn main:app --reload --port 8000   # run dev server
uv run pytest                    # run all tests
uv run pytest test_routes.py -k test_name       # run a single test
```

### Frontend (`frontend/`)
```bash
cd frontend
npm install
npm run dev          # dev server on :3000 (proxies API calls to backend separately)
npm run lint
npm run test:unit    # Vitest, single run
npm run test:unit:watch
npm run test:e2e     # Playwright: starts its OWN backend (:8001, PM_E2E=1, temp SQLite, random SECRET_KEY) and frontend (:3001); never touches pm.db
npm run test:all     # unit + e2e
npm run build         # static export -> frontend/out (consumed by Dockerfile)
```
Run a single Vitest file: `npx vitest run src/lib/kanban.test.ts`.
Run a single Playwright test: `npx playwright test tests/kanban.spec.ts -g "test name"`.

### Full stack (Docker)
```bash
./scripts/start.sh   # docker-compose build && up -d, waits on /api/health
./scripts/stop.sh    # docker-compose down
```
The Dockerfile builds the frontend (`next build` → static export), copies the output into `backend/static/`, and runs the FastAPI app with uvicorn on port 8000. `OPENROUTER_API_KEY` and `SECRET_KEY` must be set in `.env` at the repo root (see `.env.example`); docker-compose passes them through (`SECRET_KEY` via `${SECRET_KEY:?...}`, so compose fails without it) and mounts `./pm.db` for persistence.

## Architecture

### Request flow
In production (Docker), FastAPI (`backend/main.py`) mounts the static Next.js export at `/` and exposes JSON routes under `/api/*`. In local dev, the two run separately (Next dev server on :3000, FastAPI on :8000) and the frontend's `lib/api.ts`/`lib/auth.ts` talk to `API_BASE_URL`.

### Backend (`backend/`)
- `main.py` — FastAPI app setup, CORS, startup hook (`init_db` only — users/boards are created via `/api/setup`, not seeded at boot), auth endpoints (`/api/login` — matches username or email, `/api/logout`, `/api/user`, `/api/setup/status`, `/api/setup`, `/api/signup`, `/api/signup/complete`, `/api/password/forgot`, `/api/password/reset`; `_find_user` is the shared username-or-email lookup), static file mount.
- `auth.py` — `SECRET_KEY = load_secret_key()` at import: raises `InsecureSecretKeyError` if the key is missing/empty, in `INSECURE_SECRET_KEYS` (old default, `.env.example` placeholder) or shorter than 32 chars — no fallback, never echoed. JWT issuing/verification (`python-jose`), including purpose-scoped email-link tokens (`create_purpose_token`/`decode_purpose_token`; these are now used only for the Bid import preview token; signup and reset links are persistent, hashed and single-use, see `token_store.py`). Access tokens last 8h (`ACCESS_TOKEN_EXPIRE_MINUTES = 480`) and carry `pwh` and `sv` (`create_user_access_token`), password hashing (`hash_password`/`verify_password`, via `bcrypt` directly — not `passlib`, which has a known incompatibility with `bcrypt>=4.1`). No DB access here.
- `token_store.py` — `issue`/`consume`/`invalidate_for_user` for `auth_tokens` (purpose `signup` or `reset`, SHA-256 of a 256-bit random token, `expires_at`, `consumed_at`, `invalidated_at`). `consume` is one conditional UPDATE (rowcount 1 wins) and does not commit, so the caller applies its change in the same transaction. Issuing a new token supersedes earlier unused ones for the same user/email.
- `password_policy.py` — the single password rule (8-128 chars, upper, lower, number, symbol), used by the schemas and `admin_cli.py`.
- `mailer.py` — `send_email()` over SMTP (STARTTLS) configured by `SMTP_*` env vars; with `SMTP_HOST` unset nothing is sent. It never logs message bodies, links, tokens or full recipient addresses (only the subject, a masked recipient and the status; exceptions by type), and there is deliberately no dev switch to change that. `APP_BASE_URL` (in `auth.py`) sets the host in emailed links: `http://localhost:3000` for `next dev`, `http://localhost:8000` in Docker.
- `admin_cli.py` — operator CLI (`create` / `promote` / `demote` admins). Passwords only via no-echo prompt or `--password-stdin`, never argv; `create` refuses existing usernames; `demote` refuses the last admin; confirmation by retyping the username. Runs `init_db()` on `DATABASE_URL`.
- `conftest.py` — sets a random `SECRET_KEY` and a temp-file `DATABASE_URL` for every pytest run, so backend tests can't reach `backend/pm.db` (the default URL resolves there with a cwd of `backend/`).
- `deps.py` — the single `get_current_user` (parses `Authorization`, verifies the JWT, loads the `User` row) and `require_admin` (403s unless `role == "admin"`), used by both `main.py` and `routes.py`. Role is re-read from the DB on every request, not embedded in the JWT.
- `database.py` — SQLAlchemy engine/session (SQLite by default, swappable via `DATABASE_URL`), `init_db()` first runs `require_stage_events_table` (an existing database without `card_stage_events` raises `StageEventsMigrationRequired` *before* `create_all`, which would otherwise create an empty table silently), then `require_import_tables`, `require_import_revert_tables`, `require_stage_kind_column`, `require_stage_event_value_columns` and `require_complete_schema`, and only then `create_all`. All checks are read-only and run before any write, on an existing database only; a missing or empty file is created only when `PM_ALLOW_CREATE_DB=1` or `PM_E2E=1` (else `DatabaseCreationNotAllowed`), and `PM_REQUIRE_EXISTING_DB=1` demands a complete existing database (`ExistingDatabaseRequired`). `require_complete_schema` refuses an existing database lacking any table or column of the models, such as the lead columns of an old `cards` table (`DatabaseSchemaIncomplete`); nothing is altered at startup, and the migration for those columns is not written yet (`_add_missing_card_columns` remains only as an unused ALTER TABLE building block). `require_stage_kind_column` raises `StageKindMigrationRequired` instead of adding `columns.stage_kind` itself - that one decides won/lost, so it's migrated explicitly with `migrate_stage_kind.py`. With `PM_E2E=1` it also runs `check_e2e_database` at import: `DATABASE_URL` must be an explicit sqlite file under the system temp dir (never either `pm.db`), else `E2EDatabaseError`; `seed_default_board(db, creator)` seeds the shared default board (the 6 sales stages + sample leads, via `seed_pipeline`) once, called from `POST /api/setup` — not at startup.
- `models.py` — ORM models: `User` (with `role`: `UserRole.ADMIN`/`MEMBER`) → `Board` → `BoardColumn` (aliased as `Column`) → `Card`, the Part 22 Bid import tables (`ImportBatch`, `CardBidDetails` 1:1 with a card, `CardSourceRef` with DB-unique `(source_system, source_key)`, `CardImportChange` - what an import changed on an existing card, kept apart from `CardEditHistory`; written only by `bid_import_service.py`), plus `ConversationMessage` (AI chat history), `CardAction` (audit trail of AI-driven board changes — defined but never written), and `CardEditHistory` (member-edit audit trail; `Card.has_member_edits` is a Python property derived from `bool(self.edit_history)`, not a stored column). All children cascade-delete from their parent.
- `lead_options.py` — allowed lead values (`CURRENCIES`, `LEAD_SOURCES`, `PRODUCT_LINES`), stage kinds (`STAGE_OPEN`/`STAGE_WON`/`STAGE_LOST`, `STAGE_KINDS`, `StageKind`) and the seeded pipeline `PIPELINE_STAGES` (title, kind); imported by schemas (as `Literal` types), reports, seeding and the AI prompt.
- `kpis.py` — commercial KPI engine over `card_stage_events` (Part 19), with definitions in `docs/KPIS.md`. `load_board_history` makes three queries (columns, live cards, events ordered `(occurred_at, id)`) and builds per-card stays. Every KPI is a pure function of that snapshot: `won_lost`, `win_rate_closed`, `cohort`, `advancement`, `stage_time`, `velocity`, `aging`, `pipeline`, `period_kpis`. Baselines are never moves, wins or losses; durations starting at a baseline are partial (lower bounds). Money is per currency. Won/lost `values` come from each card's last won/lost event snapshot in the period (the closing value). `value_unavailable` counts events without a snapshot. The card's current value is reported apart as `current_values` and never substituted for history. `resolve_period` handles the presets and custom `[start, end+1day)` in UTC. `utcnow()` is patched in tests.
- `reports.py` — `build_board_report()`, Python-side aggregation for `GET /api/boards/{id}/report`. Money totals are always per currency (no conversion).
- `stage_history.py` — card stage history (`card_stage_events`, Part 18). A `before_flush` listener allocates new card ids above every id in `cards` and in the history (SQLite would otherwise reuse a deleted top card's id). An `after_flush` listener records `created`/`moved`/`won`/`lost`/`reopened`/`deleted` events on the same connection and transaction, for every path at once: REST, AI, undo, cascades from column/board deletion, and seeding. Type comes from `stage_kind`. `set_stage_context(db, user, source)` sets attribution: `deps.get_current_user` sets `api`, `apply_board_actions` sets `ai`, `apply_undo` sets `undo`, setup sets `seed`, the Bid import sets `import` (via `stage_context`, which restores the previous context) - with that source a new card's event is `baseline`, not `created`. `card_stage_history(db, card_id)` gives chronological events. Registered by importing it at the end of `database.py`. Every event also snapshots the card's `deal_value`/`currency` (`value_snapshot_taken` = true) in the same transaction (Part 20). `utcnow()` here is the one naive-UTC clock (kpis.py re-exports it).
- `migrate_stage_event_values.py` — explicit migration adding `deal_value_snapshot`/`deal_currency_snapshot`/`value_snapshot_taken` to an existing `card_stage_events` (Part 20). Existing events are marked "value unknown" (`value_snapshot_taken` = 0) and never back-filled. Same dry-run/backup/transaction pattern. `init_db()` raises `StageEventValuesMigrationRequired` until it's applied.
- `migrate_stage_events.py` — explicit migration creating `card_stage_events` (DDL generated from the model) plus one `baseline` event per existing card (reference state, not history). Same pattern as `migrate_stage_kind.py`, which it requires first.
- `migrate_import_tables.py` — explicit migration creating the empty Salcomp Bid import tables (Part 22). `--database` is required (no `DATABASE_URL`/`./pm.db` fallback); dry run by default; refuses out of order (the three earlier migrations first), a partial/incompatible import schema, and a second `--apply`; backup + one transaction that verifies the created schema and that every existing row is unchanged.
- `import_schema.py` — the expected schema of the Bid import tables, read back (PRAGMA) from an in-memory database built with the model DDL; `import_schema_state()` -> `absent`/`partial`/`incompatible`/`complete`. Shared by the migration and `init_db()` (`ImportTablesMigrationRequired` when absent, `ImportTablesSchemaError` when partial or different), so both accept exactly the same schema.
- `bid_excel_reader.py` — reads/validates the Salcomp Bids `.xlsx` (Part 22B) into a typed `BidReadResult` (file metadata, sheet info, per-row `RawRow` + normalized `BidRecord` with the Excel row number, file errors vs row errors vs warnings, summary). Reads only: no DB import, no writes, no logging of cell contents. The 31-column mapping is `BID_COLUMNS` (documented in `docs/DATABASE.md`). Safety: `.xlsx` content type only (no `.xlsm`/`.xls`/`vbaProject.bin`), zip size/ratio/entry limits checked before parsing, `keep_vba=False`, `keep_links=False`, XML via defusedxml (refuses to run without it). `_ExactCellParser` extends openpyxl 3.1.5's private `WorkSheetParser` so numbers come from the cell's XML text as `Decimal` (never float) and formulas without a cached value are flagged - keep openpyxl pinned and re-run `test_bid_excel_reader.py` on upgrade.
- `bid_import_preview.py` — Part 22C. `build_import_preview(read_result, stages, existing, decisions)` is a pure function: no DB import, no writes, `ImportPreview.written` is always False. It applies the approved CAT/Estágio rules (`STAGE_RULES`):
  - Award/Lost are found by `stage_kind`, open stages by title;
  - CLOSED + NOT AWARDED needs `confirm_proposed_stage`; CLOSED (BY SALCOMP), inconsistent and unknown combinations need `target_stage`.

  It also handles:
  - **Identity:** `bid_source_key` is `v1:` + the JSON array of Código and Cliente, accent-, case- and space-insensitive, keeping zeros. `bid_row_hash` is `v1:` + SHA-256.
  - **Mapping:** `CARD_FIELDS` / `BID_DETAILS_FIELDS` / `SOURCE_REF_FIELDS`, with `NOT_MAPPED_FIELDS` never imported.
  - **Duplicates and re-imports:** internal duplicates go to review. Re-imports are unchanged -> ignore, newer -> update awaiting `confirm_update`, older -> ignore, undecidable dates -> review. A stage change only moves with `confirm_move`.

  Never maps revenue to `deal_value`, Deadline to `expected_close_date`, or CPM/Líder to users; CPM is stored verbatim in `card_bid_details.cpm` (`migrate_bid_cpm.py`) and never shown in API responses.
- `bid_import_service.py` — Part 22D, the only writer of the Bid tables.
  - **`preview_bid_import`** (read-only) loads the board's stages and the existing imports.
  - **`apply_bid_import`** works in one transaction on the caller's session:
    1. inserts the batch first, taking the SQLite write lock;
    2. rebuilds the preview and refuses with `ImportConflict` unless it equals the confirmed one (concurrency, a stale preview, double confirmation);
    3. rejects unfit decisions with `ImportRejected`;
    4. creates CREATE rows (card + details + source ref) and applies confirmed UPDATE rows (mapped fields only; moves only with `confirm_move`), recording what really changed (old/new, read from the objects) in `card_import_changes` - one row per card and batch, nothing for creations, no-op updates or moves;
    5. counts, marks the batch `completed` and commits.

    Any error rolls everything back, then `record_failed_import` writes a `failed` batch (`failure_kind` validation/conflict/unexpected, `failure_reason` without cell content) in a separate transaction on its own session; a recording failure is only logged. The user id is read up front under `no_autoflush` (loading an expired user later autoflushed the caller's pending changes and held the SQLite write lock).
  - **Events:** it never writes stage events itself. It sets the session source to `import` (`stage_history.stage_context`), so the listener records `baseline` for imported cards.
- `import_routes.py` — Part 22E, the Bid import HTTP endpoints (own router, included by `main.py`), all `require_admin`: `POST /boards/{id}/imports/preview` (multipart `file` + `decisions` JSON; writes nothing), `POST /boards/{id}/imports` (same + `preview_token` + `confirm=true`), `GET /boards/{id}/imports` (paginated, newest first), `GET /imports/{batch_id}`. Parses the form itself (`request.form`) *after* the admin and Content-Length checks, so members/anonymous never get an upload read. The preview token is a `create_purpose_token` JWT binding admin, board, file SHA-256, decisions hash, latest completed batch id and a hash of the shown preview; confirm re-reads the file, rebuilds the preview and only then calls `apply_bid_import`. No import logic or transaction here - don't add any. Decisions never carry card/column ids or source keys. Needs `python-multipart`.
- `bid_money.py` — Bid revenue is INTEGER cents (`card_bid_details.revenue_*_cents`); `reais_to_cents` (Decimal/int/str only, never float; rejects >2 decimals, negatives, out of range - never rounds) and `cents_to_reais` for display. `None` = not informed, never 0. Never mixed with `cards.deal_value`.
- `migrate_stage_kind.py` — (also hosts the helpers the other two migration scripts import: `MigrationError`, `resolve_database_path`, `backup_database`, `sqlite_path_from_url`) explicit migration adding `columns.stage_kind` to a pre-Part-17 database. Dry run by default (read-only connection); `--apply` backs up to `<name>-pre-stage-kind-<time>.db.bak`, then classifies in one transaction with exactly the old report rule (title exactly "Award" → won, exactly "Lost" → lost, else open), refusing ambiguity (duplicate titles on a board) until `--set COLUMN_ID=KIND`, and verifying cards/columns are unchanged.
- `convert_to_sales_board.py` — one-off script that replaces an existing board's columns/cards with the sales stages and sample leads (users untouched). Back up `pm.db` first.
- `undo.py` — single-level, per-user undo. Card steps record `expect` (the state the change left the card in); `apply_undo` refuses (409) when a card no longer matches - another user, the AI or an import changed it since - instead of overwriting that later change; entries without `expect` (recorded before this check) are refused. Every card create/update/move/delete (REST route or AI action) records its inverse steps in that user's one `UndoEntry` row, replacing the previous one; an AI request is one entry. `apply_undo` validates all steps before applying any (409 if a card was deleted since) and always uses the entry up. Undo deliberately bypasses `can_move_card`: it restores a user's *own* last change, so a member can put back a card they advanced. Undoing a delete recreates the card with a new id; its edit history is not restored. Endpoints: `GET`/`POST /api/boards/{id}/undo`.
- `card_rules.py` — the single source of truth for member/admin card permissions (`can_move_card`, `diff_card_changes`, `apply_card_updates`, `record_member_edit`). `apply_card_updates` is the only path that writes card content/lead fields, for both REST and AI, imported by both `routes.py` and `ai_kanban.py` so the REST routes and the AI chat sidebar enforce identical rules.
- `schemas.py` — Pydantic request/response models mirroring the ORM models (`*Create`, `*Update`, `*Response`, `BoardDetail`/`ColumnWithCards` for nested board fetches, `SetupRequest`/`UserCreate`/`UserResponse` for auth, `CardEditHistoryEntry` for the history endpoint).
- `routes.py` — REST CRUD for boards/columns/cards under `/api` (board and column create/update/delete use `Depends(require_admin)`; `POST /api/ai/test` too, since it makes a paid call), undo (`/boards/{id}/undo`), lead options, the Part 14 report (`/boards/{id}/report`) and the read-only KPI endpoints (`/boards/{id}/kpis/*`, thin wrappers over `kpis.py`), the AI chat endpoint `POST /api/boards/{id}/ai`, and admin-only user management (`GET`/`POST /api/users`, via `Depends(require_admin)`). Boards are shared, not owned — routes look up `Board.id` only, never filter by who created it. `delete_card` and the backward-move branch of `move_card` are admin-only (via `card_rules`); `GET .../cards/{id}/history` returns a card's `CardEditHistory` entries.
- `ai.py` — low-level OpenRouter client wrapper (`call_ai`, `test_ai_connectivity`, `AIError`).
- `ai_kanban.py` — builds board-state context and conversation history for the AI, defines the system prompt requiring structured JSON output (`{response, actions[], confidence}`), and applies returned `actions` (create/update/move/delete) back onto the board via `apply_board_actions`, which takes the requesting `current_user` and applies the same `card_rules` checks as the REST routes (a member can't get the AI to delete a card or move it backward on their behalf).
- Tests are colocated (`test_*.py`), run with `pytest` + `TestClient`.

### Frontend (`frontend/src`)
- `app/page.tsx` → renders the top-level component tree; `ProtectedRoute` gates on setup-status/auth (`SetupPage` when no users exist yet, else `LoginPage`), `KanbanWithSidebar` composes the board with `AIChatSidebar`, `ManageUsersPage` is admin-only (toggled from the header). `SignupPage` (email request) and `ForgotPasswordPage` are reached from `LoginPage`; `SetPasswordPage` (password + confirm, parameterized by title and submit function) is shown when the URL has `?signup_token=` or `?reset_token=` (read from `window.location.search` in the bootstrap effect, not `useSearchParams`, which would need a Suspense boundary under static export).
- `components/KanbanBoardAPI.tsx` — the persisted, API-backed board (replaces the older local-state-only `KanbanBoard.tsx`/`lib/kanban.ts` demo, which is still used in its own tests). Talks to the backend via `lib/api.ts`; receives `role` as a prop (threaded down from `ProtectedRoute`) to gate card deletion and to block a member's backward drag client-side before the backend's 403 (defense in depth, not the real gate).
- `KanbanBoardAPI.tsx` has a sticky Undo bar at the top of the board: it re-reads `GET .../undo` after every successful change and reloads the whole board after an undo. Its root uses `overflow-clip`, not `overflow-hidden` - the latter makes it the scroll container and the bar stops sticking.
- `components/DashboardPage.tsx` — Executive Dashboard (Part 21), header button "Dashboard", all roles. Uses only `/kpis/*` data, formatted on the client: period filters (presets, custom range, compare); coverage banner; headline tiles; closing values versus "value unavailable" versus today's value (never substituted); conversion; time in stage; open pipeline; aging; data quality. A response is shown only while its `key` matches the current filters, never another period's numbers. A previous period that ended before tracking started reads "not tracked", never 0. `components/ReportBlocks.tsx` holds the `StatTile`/`Section`/`Totals`/`StageBars` and table classes shared with `ReportsPage`. `components/LoadingScreen.tsx` is the shared spinner. `lib/format.ts` adds `moneyTotalsToNumbers`, `formatRate` (null shows "-", never 0%), `formatDays` (with a lower-bound mode) and `formatPeriodDates` (UTC dates, end inclusive).
- `components/LeadEditModal.tsx` — the lead fields form (opened by a card's "Edit lead" button); sends only changed fields, with `null` to clear. `components/ReportsPage.tsx` — KPI tiles, leads-by-stage bars, closing-soon table and breakdowns, with salesperson/product filters; opened from the header "Reports" button (all roles). Selects are fed by `GET /api/lead-options`, which members can read (unlike admin-only `GET /api/users`).
- `components/KanbanCard.tsx` — title/details are always-editable `<input>`/`<textarea>` (committed on blur, not per-keystroke, to avoid an API call — and a member-edit-history row — per character typed); dragging is via a dedicated handle button, not the whole card, since the card's surface is otherwise all editable text. Shows an "M" badge when `card.hasMemberEdits`, opening `CardHistoryModal` (the project's first true overlay/modal — no prior modal pattern existed).
- `lib/auth.ts` — stores the JWT + role (e.g. localStorage), exposes `API_BASE_URL`, `getAuthHeader()`, `getSetupStatus()`/`setupAdmin()`, and `isAdmin()` (UI-only gating — the backend independently re-checks role on every admin request).
- `lib/api.ts` — typed fetch wrapper (`apiCall`) for the board/column/card/AI/user/report/undo endpoints and the `/kpis/*` endpoints (typed `Kpi*`/`MoneyTotals` mirroring `schemas.py`, `getKpiSummary/Conversion/StageTime/Aging/Pipeline`); normalizes HTTP and network errors into `ApiError` (`getErrorMessage(err, fallback)` narrows a caught `unknown` error down to its `.detail`).
- Drag-and-drop uses `@dnd-kit` (core + sortable); column/card components (`KanbanColumn`, `KanbanCard`, `KanbanCardPreview`, `NewCardForm`) are shared between the demo and API-backed boards. Card/column titles are Playwright-unfriendly for `getByText` (they're input values) — e2e tests match cards via a `data-title` attribute instead.
- Styling: Tailwind CSS 4, with the app color palette defined as CSS variables in `app/layout.tsx` (`--primary-blue #209dd7`, `--secondary-purple #753991`, `--accent-yellow #ecad0a`, `--navy-dark #032147`, `--gray-text #888888`).

### Non-obvious bugs already fixed (don't reintroduce)
- `models.py`: a model class literally named `Column` shadowed SQLAlchemy's own `Column` import and broke under SQLAlchemy 2.0.36's type-annotation syntax — now aliased as `BoardColumn` (`Column = BoardColumn` for back-compat). `ConversationMessage.meta_data` is named that way (not `metadata`) because `metadata` collides with `Base.metadata`.
- `ai.py`: OpenRouter's base URL is `https://openrouter.ai/api/v1` — `.io` 404s.
- `ai_kanban.py`: `call_ai_with_board()` must actually prepend `{"role": "system", "content": SYSTEM_PROMPT}` to the message list (plus `response_format: {"type": "json_object"}` in `ai.py`'s `call_ai()`) or the model free-forms text instead of structured JSON, and `apply_board_actions()` silently never runs.
- `KanbanBoardAPI.tsx`: columns and cards are separate SQL tables with independent autoincrement ids, so a column and a card can share a numeric id. dnd-kit keys all draggables/droppables in one id-keyed map, so raw numeric ids collide. Ids are prefixed (`col-${id}` / `card-${id}`) before being handed to `KanbanColumn`/`KanbanCard`, then translated back to numeric ids in callbacks — don't strip that prefixing.
- `auth.ts` / `api.ts`: use the `API_BASE_URL` constant, not relative paths — relative `/api/...` calls only work when frontend and backend share an origin (the Docker/static-export setup), and 404 against Next.js itself when run as separate dev servers.
- `routes.py` used to have its own `get_current_user` that ignored the `Authorization` header and always loaded a hardcoded username — meaning no board/column/card/AI route ever validated a bearer token. Fixed by unifying on `deps.get_current_user`; don't reintroduce a second, route-file-local auth dependency.
- Backend tests using an in-memory SQLite engine (`create_engine("sqlite:///:memory:")`) need `poolclass=StaticPool` + `connect_args={"check_same_thread": False}`, or `TestClient` requests intermittently fail with `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread` — see `test_auth.py`/`test_routes.py`'s `test_db` fixture.
- Central `card_rules.is_admin` must recognize a `CompanyContext` through its `is_global_admin` property, never by comparing its role string to `"admin"` (the global administrator's role is `"super_admin"`; `"admin"` is reserved and grants nothing in Phase 1). The legacy `User.role == "admin"` branch stays for the single-database mode.
- `ai_kanban.py`'s `apply_board_actions()` must receive and check `current_user` for every action — it's a second entry point onto the same cards as the REST routes, so skipping the `card_rules` checks there (as an early version did) lets a member delete/backward-move/untracked-edit a card just by asking the AI to do it, silently bypassing the REST routes' 403s.
- `auth.py` used to fall back to a hardcoded `SECRET_KEY` (public in this repo) when the env var was unset - anyone could forge an admin token. Never reintroduce a default; `load_secret_key()` refuses missing/known/short keys. Board/column write routes and `/api/ai/test` used to accept any logged-in user (a self-signed-up member could delete the whole board) - they're `require_admin` now; keep structural changes admin-only.
- `auth.py`: `verify_token` must reject any JWT carrying a `purpose` claim. Signup-link tokens share `SECRET_KEY` and a `sub` (the email, which is also the username), so without that check a signup link would work as a bearer token once its account exists.
- Bid revenue (`card_bid_details`) was first drafted as `NUMERIC(18, 2)`; SQLite rounds that past ~15 significant digits. It's INTEGER cents converted via `bid_money.py` - don't reintroduce NUMERIC/FLOAT money there or convert through float.
- Import changes must never go to `card_edit_history`: `has_member_edits` is `bool(edit_history)` and backs the "M" badge ("a member changed this"). They go to `card_import_changes`.
- `undo.py`: undo steps used to store only old values and restore them unconditionally, silently overwriting any later change to the card (another user's, the AI's, an import's). Every card step must carry `expect`, and `apply_undo` must check it before applying anything.
- `stage_history.py`: never write stage events from routes or services - the flush listener is the single writer, and a second writer would duplicate events. Never let SQLite pick card ids (the `before_flush` allocator prevents a deleted card's history being spliced onto a new card that reuses its id). Never give `card_stage_events` a FK/relationship to `cards` that cascades: history must survive card deletion.
- Reports used to classify won/lost by comparing column titles with "Award"/"Lost", so renaming a column silently changed the KPIs. Always key on `Column.stage_kind`. Backend rules (`routes._check_stage_kind`): at most one won and one lost stage per board, and a column's kind can't change while it holds cards (that would silently reclassify its opportunities).
- Playwright used to start only a frontend and hit whatever backend was on :8000 - the dev one, with `backend/pm.db`. Now `playwright.config.ts` starts its own backend with `PM_E2E=1` on a temp DB, `tests/helpers.ts` has no URL fallback, and `tests/e2e-setup.ts` refuses a backend whose `/api/health` lacks `test_mode: true` and fails the run if a dev `pm.db` changed. Don't add a fallback URL. The E2E `next dev` uses `distDir` `.next-e2e` (`PM_E2E_DIST_DIR`), because `next dev` locks its dist dir and the developer's own server holds the default one.
- E2E drags: `dragCardToColumn` waits for the `drag-overlay` testid to detach before and after each drag. dnd-kit ignores a new drag while the previous drop animation runs, so dragging the same card twice in quick succession silently did nothing. Column title testids must not start with `column-` (tests select columns by that prefix) - the member read-only title is `stage-title`.
- `KanbanColumn.tsx`: the column title is committed on blur/Enter (a `draft` state that falls back to the saved title), not per keystroke - per-keystroke saves fired an API call per character. Members get a plain heading, not an input.
- `KanbanBoardAPI.tsx` collision detection is `pointerWithin` with a `closestCenter` fallback, not plain `closestCenter`: lead cards are tall, one long column stretches every column in the grid row, and `closestCenter` then measures a drop into a short column's empty area against that column's far-away center - the card silently snaps back into another column.
- `main.py` `reset_password`: single use comes from `token_store.consume` (conditional UPDATE) in the same transaction as the password change; the `pwh`/`sv` claims only end earlier sessions. Never consume and change in separate commits.
- `KanbanCard.tsx`: title/details became `<input>`/`<textarea>`, not static text — (1) don't spread dnd-kit's drag `listeners`/`attributes` across the whole card, only a dedicated handle button, or clicking into a field to edit competes with picking the card up; (2) in a narrow column, an unconstrained `flex-1 min-w-0` content div can get squeezed to literally 0 width by fixed-size siblings (the drag handle, delete button) — the action row lives *above* the content, not beside it, so title/details always get the card's full width; (3) e2e/unit tests must match cards via `getByDisplayValue`/`[data-title=...]`, not `getByText` (an input's value isn't text content).

## Coding standards (from AGENTS.md)

- Use latest stable versions of libraries and idiomatic patterns.
- Keep it simple: no over-engineering, no unnecessary defensive programming, no speculative features.
- Be concise; no emojis, ever.
- When debugging, find the root cause before attempting a fix — don't guess.
