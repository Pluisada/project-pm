## Project

Salcomp sales lead tracker on a Kanban board: cards are leads, columns are sales stages (1st Contact, F2F Meeting, RFI, Proposal, Award, Lost). A column's commercial meaning is its `stage_kind` (`open`/`won`/`lost`), never its title. Cards carry lead fields (company, contact, deal value + currency, close date, source, product line, salesperson); a Reports screen and an Executive Dashboard (KPIs) aggregate them; an AI chat sidebar can create/edit/move cards. Next.js frontend (static export), FastAPI backend serving it at `/`, SQLite, one Docker container. AI via OpenRouter (`openai/gpt-oss-120b`).

Auth and roles:
- The first user (setup screen or `create_commercial_db.py`) is admin; HTTP `/api/setup` is closed unless `PM_SETUP_TOKEN` (>=32 chars) is set and sent as `X-Setup-Token` (docs/SECURITY.md section 2). Further admins only via `backend/admin_cli.py`; no HTTP path grants admin. Admins invite members by email (Manage Users): the account is unverified with no usable password until the invitee follows the emailed single-use link (reset flow); self-sign-up is limited to `SIGNUP_ALLOWED_DOMAINS` plus the individual `SIGNUP_ALLOWED_EMAILS` (member, email = username) via a single-use `/?signup_token=` link, and the account exists only once that link verifies the email; "Forgot my password?" sends a single-use 1-hour `/?reset_token=` link and always answers the same way, whether or not the account exists. Signup/reset tokens are random, stored only as SHA-256 in `auth_tokens`. `SECRET_KEY` must be set (>=32 chars, no default) - see `docs/SECURITY.md`.
- Sessions: access tokens last 8 hours and carry `pwh` (password fingerprint) and `sv` (the user's `session_version`). `POST /api/logout` bumps `session_version`, which ends **all** of that user's sessions on every device; a password change or reset does the same. Passwords need 8-128 chars with an upper-case letter, a lower-case letter, a number and a symbol (`password_policy.py`, enforced by every endpoint and `admin_cli.py`). No access without a verified email (`users.email_verified_at`).
- Boards are shared across users; board/column structure changes are admin-only.
- Cards: everyone sees every card. A member edits and moves only cards assigned to them (unassigned cards: admin only); only admins assign/reassign (a member-created card is assigned to its creator, audited as `create` + `assign`) and delete. Members move cards only forward (or reorder in a column); only admins move backward. Review flags (central mode, `card_reviews.py`): a Sales Member's edit flags Admin and Super Admin; an Admin-level backward move flags the Super Admin; a company Admin moving a card into LOST flags the Super Admin (`lost_move`, decided 2026-10-24); ordinary forward moves, Admin/Super Admin edits and a Super Admin's own moves flag nothing. Undo of a move also requires owning the card then. Assignment changes and deletions are written to `audit_events`. A member's title/details edit goes to `card_edit_history` and sets the "M" badge; admin edits aren't logged. REST, AI chat and undo share these rules through `backend/card_rules.py`.
- Bid imports (Part 22) are admin-only.

## Architecture

Prod: FastAPI mounts the static export at `/` and serves `/api/*`. Dev: Next on :3000, FastAPI on :8000; the frontend uses `API_BASE_URL`.

### Backend (`backend/`)
- `main.py` auth endpoints + static mount; `auth.py` JWT, bcrypt (not passlib), `load_secret_key()`; `token_store.py` persistent single-use signup/reset tokens (hash only, atomic consume); `password_policy.py`; `rate_limit.py` limits login/signup/forgot/Bid import; `deps.py` the single `get_current_user` / `require_admin` (role re-read from DB each request); `mailer.py` SMTP (never logs bodies, links or full addresses; with `SMTP_HOST` unset nothing is sent).
- `database.py` engine, `init_db()` with startup guards that refuse an un-migrated DB (`StageKindMigrationRequired`, `StageEventsMigrationRequired`, `StageEventValuesMigrationRequired`, `ImportTablesMigrationRequired`); `PM_E2E=1` forces a temp DB. `conftest.py` gives every pytest run a random key and temp DB.
- `models.py` ORM (`User` > `Board` > `BoardColumn` > `Card`, plus history/import tables); `schemas.py` Pydantic; `lead_options.py` allowed values and the seeded pipeline.
- `routes.py` boards/columns/cards, undo, report, `/kpis/*`, AI chat, users; `import_routes.py` Bid import endpoints (below); `ai.py` OpenRouter client; `ai_kanban.py` prompt + `apply_board_actions`.
- `card_rules.py` the only path that writes card content/permissions, used by REST and AI. `undo.py` single-level per-user undo; steps carry `expect` and `apply_undo` refuses (409) if the card changed since.
- `stage_history.py` writes `card_stage_events` from flush listeners (the only writer); `kpis.py` + `reports.py` read them; Deal Value is always USD (`lead_options.DEAL_CURRENCY`; legacy `cards.currency` codes ignored on read, no conversion). See `docs/KPIS.md`.
- Production strategy (2026-10-23): the first VPS installation uses fresh databases built by `create_identity_db.py`, `identity_admin_cli.py bootstrap` and `create_company_db.py` (complete current schema; no migration scripts needed) and populated from approved files; see docs/DEPLOYMENT.md, "Initial production installation". **Executed on 2026-10-26 (observed, `docs/PRODUCTION.md`):** four fresh databases were created in the release image on the VPS, with one bootstrapped Super Admin and no boards or cards; nothing was populated from files, and no database, backup, `.env` or other local test data was copied from the Mac. `create_commercial_db.py` builds a new clean database (schema, admin, board and stages, no cards) at an explicit path that must not exist; the app is pointed at it with `DATABASE_URL`. See `docs/DATABASE.md`.
- Migrations are explicit scripts (dry run by default): `migrate_stage_kind.py`, `migrate_stage_events.py`, `migrate_stage_event_values.py`, `migrate_import_tables.py --database <path>` (`import_schema.py` defines the expected schema), `migrate_import_revert.py`, `migrate_bid_cpm.py` (`card_bid_details.cpm`), `migrate_legacy_bid_confidence.py --database <abs> [--expect-sha256 <hash> --apply]` (legacy single-database file: adds `cards.confidence_level`, drops the obsolete Bid confidence columns; exclusive, content-verified backup under the write lock; procedure in `docs/MIGRATION_PROTOCOL_BID_CONFIDENCE.md`), `migrate_card_contact.py --company <slug> | --database <abs path>` (`cards.contact_email`, `cards.contact_phone`; required in the company schema, so every database needs it before this code runs; docs/DEPLOYMENT.md), `migrate_auth_security.py --database <path>` (session_version, email_verified_at, `auth_tokens`, `audit_events`). `migrate_deal_years.py --database <path> --year Y` (`cards.deal_value_next_year`, `cards.deal_year`; `deal_value` is the amount for `deal_year`, the card shows the sum; year change only via `migrate_deal_year_rollover.py`; reports/KPIs still use `deal_value` alone). Startup never migrates and never creates a missing database (`PM_ALLOW_CREATE_DB=1` is the explicit opt-in).
- Central company databases: `company_schema.py` (read-only validator, version 4), additive tables by `init_company_card_reviews.py`, `init_company_card_loss.py`, `init_company_excel_imports.py`, `init_company_products.py` (independent, dry run by default, idempotent), and `diagnose_company_schema.py` (read-only report of every missing element, exit 0/1/2). Upgrade procedure, backup prerequisites and what is not validated: `docs/DEPLOYMENT.md`, "Existing company databases". No unified upgrade command, by decision.
- Bid import (Part 22): `bid_excel_reader.py` (read/validate .xlsx, no DB) > `bid_import_preview.py` (pure preview engine) > `bid_import_service.py` (the only writer of the Bid tables, one transaction, records failed attempts, import changes go to `card_import_changes`, never `card_edit_history`) > `import_routes.py` (parse, check the signed `preview_token`, translate errors; no import logic or transactions). `bid_money.py` revenue as integer cents.

### Frontend (`frontend/src`)
- `app/page.tsx` > `ProtectedRoute` (setup/login/auth gate) > `KanbanWithSidebar` (`KanbanBoardAPI` + `AIChatSidebar`); `ManageUsersPage`, `ReportsPage`, `DashboardPage`, `LeadEditModal`, `CardHistoryModal`; signup/reset screens read `?signup_token=` / `?reset_token=` from `window.location.search`.
- `BidImportPage` (+ `BidImportRows`, `BidImportHistory`, `lib/bidImport.ts`): admin-only Import Bids screen; it sends only explicit decisions and lets the backend say which rows need what.
- `lib/api.ts` typed fetch wrapper (`ApiError`), `lib/auth.ts` JWT in localStorage + `API_BASE_URL`; UI role gating is defense in depth only.
- dnd-kit drag-and-drop; Tailwind 4; palette in CSS variables in `app/layout.tsx`.

### Don't reintroduce (full list in `docs/CLAUDE-reference.md`)
- Access tokens must carry `pwh` and `sv` (`auth.create_user_access_token`) and `deps.get_current_user` must validate them against the user's current `password_fingerprint` and `session_version`; never issue or accept a token without them. Logout must bump `session_version`.

## Real-application validation (mandatory for every batch and session)

Automated tests, mocks, simulated services and disposable test databases remain in use, but none of them is final functional validation by the user. Passing tests (level A) does not mean the running application (level B) was checked or that the user accepted it (level C). Procedure, environment rules and the report template: `docs/TESTING.md`.

For every implementation batch:
1. Run the relevant automated tests and checks.
2. Start or update the real frontend and backend processes so they run the implemented code (restart only what is needed to load it; the developer does this, not the user).
3. Verify both are running and reachable and the startup logs show no relevant errors.
4. Give the user the exact URL, the features ready to test, the steps and the limitations.
5. State separately what automated tests verified and what was exercised in the running application.
6. Keep the batch open until the user has tested and accepted it; on a reported defect, fix, rerun the relevant tests, update the running application and offer another cycle.

Never claim a feature works because tests or mocks passed, never claim manual validation that was not actually done in the running application, and never silently substitute a simulation for an unavailable dependency (SMTP, other integrations): say exactly what can and cannot be validated, and never claim real email delivery was tested without SMTP. Do not mark a phase accepted before the user confirms.

### Permanent policy: the real local runtime and real email (decided 2026-10-24; details in `docs/TESTING.md` and `docs/DEPLOYMENT.md`, "Real local runtime")

- **Manual validation happens in the actual running application**, never in a copied-database stack, simulated server or mocked frontend: runtime directory `~/Library/Application Support/SalcompSalesPipeline`, backend `8010`, frontend `3010`, URL `http://127.0.0.1:3010`, databases `central/` (identity, Salcomp, Lity, Valor-Log; fictional test data kept for local validation only: the production databases were created fresh on the VPS on 2026-10-26 and no contents of these databases were copied into production, see `docs/PRODUCTION.md`). The old 3011/8011 copy stack is retired as an acceptance environment. Automated tests keep using disposable databases; they never replace manual acceptance.
- Before asking the user to test: verify the code version being served, start or restart the real app when necessary and safe, check backend and frontend health, confirm the intended databases, then give the exact URL and short steps. If the real app cannot start, report the blocker; the manual-testing requirement is then not met.
- Real databases: back up before any schema or destructive change, apply migrations only through the documented procedure after inspecting the exact change, check the schema with `diagnose_company_schema.py` before starting. **During testing and manual validation, never touch production** (it is never a test, rehearsal or migration target for local work). **Production changes** (configuration, databases, deployments, restarts, backups, NPM, DNS, email sends) **require the owner's explicit authorization for that specific change and must follow `docs/PRODUCTION.md` and the applicable deployment procedure** (`docs/VPS_DEPLOYMENT_PLAN.md`, `docs/DEPLOYMENT.md`); unapproved production changes remain prohibited. Do not stop another active stack unless needed and verified safe.
- **Real email is tested at two levels.** Level A: mocked providers in automated tests (success, connection failure, authentication failure, missing configuration, rejection, retries); they never send mail or need real credentials. Level B: any change touching invitations, password resets, email templates, links, delivery status or SMTP configuration is also prepared in the real app with the configured SMTP provider.
- Level B preparation: inspect the runtime's mail configuration without exposing secrets; load the `SMTP_*` settings from the repository `.env` into the running backend (the runtime scripts unset them, so use a temporary launcher outside the application directory; never edit `.env` or the established scripts); `APP_BASE_URL` is `http://127.0.0.1:3010` in the real runtime and may stay `http://localhost:3000` in `.env` for development (do not change it for the runtime); `SMTP_FROM` must be the authenticated account or a provider-verified alias; restart the real backend if needed; check health and logs for SMTP errors; **ask the user to specify or confirm the recipient before any real send, and send to no one else**.
- Report email results in five separate levels and claim no more than the evidence: (1) request persisted, (2) SMTP submission attempted, (3) SMTP server accepted, (4) provider delivery status if available, (5) receipt in the mailbox, only if the user confirmed it. Without working SMTP, state that real delivery is blocked; never present mocks as proof of delivery.
- Never print or document secrets (SMTP password, API keys, invitation or reset tokens). Keep the task open until the user completes manual validation. The final-checklist for every relevant change is in `docs/TESTING.md`.

## Coding standards

Latest stable libraries and idiomatic patterns; keep it simple (no over-engineering, speculative features or needless defensive code); be concise; no emojis; find the root cause before fixing.
